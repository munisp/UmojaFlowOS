# Keycloak realm boundary

Import `realm-umojaflowos.json` only into a TLS-protected Keycloak deployment controlled by the platform security owner. The client secret is intentionally omitted and must be generated in Keycloak, stored in a managed secret store, and injected into APISIX and approved server workloads.

The realm defines only `admin`, `compliance_officer`, `treasury_operator`, and `auditor`. The application claim mapper is deny-by-default; unknown roles must not acquire platform permissions.

## `umojaflowos-admin-api` client

Backs the console's "onboard operator" action (Governance → Operator access) and the Admins & Operators directory (Admins), which create and manage identity-provider accounts directly instead of requiring separate Keycloak-console access. It is a service-account client scoped to `manage-users` only — never `admin-cli` and never the broad `realm-admin` role — so a compromised application credential cannot manage realm settings, other clients, or roles beyond creating/reading/updating users. Its secret is generated in Keycloak the same way as the gateway client's, stored in the managed secret store, and injected as `UMOJA_KEYCLOAK_ADMIN_CLIENT_ID` / `UMOJA_KEYCLOAK_ADMIN_CLIENT_SECRET`. Leaving those unset disables both features rather than failing sign-in: the console falls back to its existing "grant a role once someone has already signed in" path, and the directory reports itself unavailable.

`UMOJA_KEYCLOAK_ADMIN_BASE_URL` (optional) names where the `/admin/realms/*` REST API is actually reachable, separately from `UMOJA_KEYCLOAK_ISSUER`. These are not the same surface: a front door that publicly proxies `/realms/*` (the OIDC endpoints) has no obligation to also proxy `/admin/*`, and many real deployments deliberately keep the admin API internal-only. When unset, the admin base URL is derived from the issuer, which only works if the admin API happens to be reachable at that same public host — true for a from-container-network internal issuer, false the moment a public-facing proxy sits in front of it. Local dev behind the Caddy front door in this repo's `infra/keycloak` setup is exactly that latter case: Caddy proxies only `/realms/*` and `/resources/*`, so `UMOJA_KEYCLOAK_ADMIN_BASE_URL` must point directly at Keycloak (e.g. `http://localhost:8081`), bypassing Caddy entirely — safe because these calls originate server-side, never from the browser.
