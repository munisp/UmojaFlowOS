05 · Security compliance
Authentication and authorization are separate gates
A successful TLS handshake proves identity but does not grant access. The gRPC boundary requires both STRICT mesh mTLS and an explicit principal allowlist.

Layer 1: Authentication

  • STRICT PeerAuthentication: Rejects all plaintext and mesh-bypass attempts at the pod level.
  • ISTIO_MUTUAL: Enforces mesh-managed certificates for all internal gRPC traffic.
  • TLS 1.3: Modern cipher suites only; no legacy protocol fallback permitted.

Layer 2: Authorization

  • Exact Principals: Access restricted to specific SPIFFE-like identities (control-plane, reconciliation).
  • Method Constraint: Only POST operations on port 8443 are permitted by the AuthorizationPolicy.
  • Default Deny: Any principal not explicitly allowlisted receives a PermissionDenied response.

Negative test evidence

$ grpcurl -plaintext payment-engine:8443 list -> REJECTED (STRICT mTLS)
$ grpcurl --cert unallowlisted.crt payment-engine:8443 list -> PERMISSION_DENIED (RBAC)

Control: Handshake evidence and negative authorization logs are required for every release SHA.
