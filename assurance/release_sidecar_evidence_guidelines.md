# Release manifest and sidecar evidence guidelines

The release manifest is intentionally strict. Its root, artifact entries, and approval entries use `additionalProperties: false`; metadata that does not belong to the release contract must be stored in a separately hashed sidecar file.

## Strict manifest rule

The only permitted release-manifest root fields are `release_sha`, `environment`, `created_at`, `artifacts`, and `approvals`. The only permitted artifact fields are `evidence_id`, `path`, `sha256`, and `run_id`. The only permitted approval fields are `role`, `subject`, `release_sha`, and `approved_at`.

Do not add `signature`, `public_key`, `key_id`, `region`, `cluster`, `provider`, `notes`, or other custom properties to those objects. Such fields make the JSON Schema invalid. Store them in a sidecar instead.

## Sidecar layout

Sidecars must be stored under the evidence bundle and referenced by the applicable E-item report, not added as custom manifest properties:

```text
<bundle-root>/
  release.json
  E-01/
    report.json
    provenance.json
    provenance.json.sha256
    signer-verification.json
  E-04/
    report.json
    cluster-topology.json
    reconciliation-summary.json
  E-06/
    report.json
    rollout-receipt.json
  E-08/
    report.json
    restore-receipt.json
    chaos-recovery.json
```

Each sidecar must be a nonempty regular file with a stable relative path. Sensitive credentials, private keys, bearer tokens, database URLs, raw customer data, and unredacted personal data must never be placed in a sidecar.

## Canonical JSON sidecars

For JSON sidecars, use UTF-8, deterministic key ordering, no insignificant whitespace, and a terminating newline:

```bash
jq -S -c . raw-sidecar.json > canonical-sidecar.json
printf '\n' >> canonical-sidecar.json
sha256sum canonical-sidecar.json > canonical-sidecar.json.sha256
```

If the sidecar contains timestamps, use ISO-8601 with an explicit timezone. If it contains identifiers, use the immutable release SHA, staging run ID, image digest, database migration run ID, or external execution correlation ID. Never use a mutable image tag as the sole binding identifier.

## Required sidecar metadata

Every sidecar report should carry, either in its own schema or in the parent E-item report, these provenance values:

| Field | Requirement |
|---|---|
| `evidence_id` | One of E-01 through E-09 |
| `release_sha` | Full lowercase 40-character Git SHA |
| `run_id` | Unique staging execution identifier |
| `generated_at` | Timezone-qualified ISO-8601 timestamp |
| `source_system` | Specific staging system or controlled runner |
| `source_identity` | Non-secret runner/service identity |
| `result` | Explicit pass, fail, or indeterminate state |
| `artifact_sha256` | Digest of the referenced artifact when applicable |

The sidecar must state whether the result was generated by a real staging system, a CI contract fixture, a simulator, or a local test. CI fixtures and simulators must never be labeled as real staging evidence.

## Hash and custody procedure

After all sidecars are finalized, calculate digests from the exact immutable files:

```bash
find "$EVIDENCE_DIR" -type f -not -name '*.sha256' -print0 \
  | sort -z \
  | xargs -0 sha256sum > "$EVIDENCE_DIR/SHA256SUMS"
sha256sum "$EVIDENCE_DIR/SHA256SUMS" > "$EVIDENCE_DIR/SHA256SUMS.sha256"
```

Review the file list before hashing so secrets or temporary logs are excluded. Preserve the evidence bundle in an access-controlled, append-only or WORM-capable location. The release manifest must use explicit relative artifact paths and the digest of the final report file, not the digest of a mutable directory or a glob.

## Approval and signature separation

Approval objects remain limited to their four schema-approved fields. If governance requires cryptographic approval signatures, keep detached signatures, public-key fingerprints, certificate chains, and verification logs as protected sidecars. Bind each signature to the canonical manifest digest and record the signer identity and verification result in a separate governance sidecar. The current release verifier validates manifest structure, artifact digests, SHA binding, and approval independence; it does not itself validate detached approver signatures.

## CI enforcement

The pull-request workflow runs `scripts/infra/validate_release_manifest_schema.py` before `verify_production_release_evidence.py`. A custom field produces a deterministic failure such as:

```text
manifest schema validation: FAILED: $['artifacts'][0]: Additional properties are not allowed ('custom_field' was unexpected)
```

Move the metadata into a sidecar, reference it from the E-item report, recalculate the relevant digest, and rerun both validators. Do not weaken `additionalProperties: false` merely to accommodate an operational convenience field.
