# TigerBeetle Consensus-Loss and DR Failover Controls

**Scope:** Authorized staging only  
**Purpose:** Define failure scenarios and rollback triggers for E-04, E-06, and E-08 validation  
**Safety rule:** No scenario may use live customer funds or unapproved provider activity. An ambiguous financial outcome is held, reconciled, and escalated; it is never retried blindly.

## Control model

The test has four states: **healthy**, **degraded**, **fenced/held**, and **recovered**. A transfer may be submitted only while the ledger cluster, payment engine, signer, provider rail, and reconciliation store are healthy and the controlled-live policy permits the operation. During degradation, new settlement is reduced or suspended. During fencing, new settlement is disabled and unresolved transactions remain in an explicit UNKNOWN/held state until a read-only status or reconciliation decision is available. Recovery is not complete until the ledger and PostgreSQL state reconcile and an authorized operator releases the hold.

## TigerBeetle failure scenarios

| ID | Injected failure | Expected observable signals | Immediate safe action | Rollback trigger | Evidence required |
|---|---|---|---|---|---|
| TB-F01 | Loss of quorum or insufficient healthy replicas | Cluster health reports quorum failure; transfer requests fail or become unavailable; health alert fires. | Fence settlement and stop new transfer submissions. Preserve the last known ledger and PostgreSQL snapshots. | Any attempt to settle while quorum is unavailable, or inability to establish a trusted quorum within the approved window. | Cluster health, node status, alert event, fencing log, held-transfer list, operator decision. |
| TB-F02 | Network partition isolates a ledger node or replica | Divergent connectivity; node cannot confirm cluster membership; coordinator sees timeout/UNKNOWN. | Do not retry the financial command. Mark the operation UNKNOWN/held and perform a read-only status/reconciliation query. | Conflicting node views, inability to prove the authoritative cluster view, or any duplicate-submission risk. | Toxiproxy/network configuration, request IDs, coordinator state transition, read-only query, reconciliation output. |
| TB-F03 | Consensus commit latency exceeds the transaction deadline | Ledger request times out; provider/payment engine may not know whether commit occurred; latency alert fires. | Cancel the caller wait without assuming failure; retain idempotency key and query status. | No authoritative status within the bounded reconciliation period, or mismatch between provider and ledger status. | Latency histogram, timeout, idempotency record, status response, final decision record. |
| TB-F04 | Leader/primary process crash during transfer | Process restart or node health failure; in-flight request has no terminal response. | Fence the affected execution worker; reconcile by idempotency key before any retry. | Restarted worker cannot prove lease ownership, or a second worker attempts execution without a verified lease. | Process events, lease token, worker fencing, reconciliation result, duplicate-prevention assertion. |
| TB-F05 | Corrupted or mismatched account binding | Account ID, asset, debit/credit owner, or currency does not match approved map. | Reject the transfer before network transmission and quarantine the test case. | Any transfer reaches the ledger with an unapproved account or asset binding. | Approved account map, validation error, no-submit trace, quarantine record. |
| TB-F06 | Replayed or duplicate idempotency key | Same key is submitted concurrently or after timeout; duplicate request detected. | Return the original decision or keep both requests held until authoritative reconciliation. | More than one terminal settlement for one logical payment, or missing payload SHA-256 match. | Concurrent request log, key binding, payload hash, terminal-decision table, reconciliation result. |
| TB-F07 | Ledger/PostgreSQL disagreement | Reconciliation reports a missing posting, extra posting, amount mismatch, or status mismatch. | Stop settlement and open a financial-integrity incident. Do not manually edit evidence rows. | Any unexplained discrepancy; zero-tolerance for silent correction or forced success. | Before/after balances, transfer facts, posting intents, reconciliation report, incident and approval record. |
| TB-F08 | Recovery produces a stale or split-brain node | Recovered node reports old state or cannot prove current membership. | Keep node out of service; require cluster rejoin and authoritative state verification. | Stale node accepts writes or any read is used as authoritative without cluster confirmation. | Recovery logs, membership/quorum proof, node fencing, post-recovery consistency check. |

## TigerBeetle rollback procedure

First, stop new settlement at the router and disable automatic fallback that could create a second financial command. Second, preserve all request IDs, idempotency keys, payload hashes, leases, provider responses, and ledger outputs. Third, query status through a read-only path and compare the result with PostgreSQL payment state and ledger transfer facts. Fourth, if the status is unresolved, retain the payment in UNKNOWN/held state and escalate to the Treasury/Ledger Witness. Fifth, restore or fail over only through the approved staging runbook, then repeat reconciliation. Finally, release the hold only after the ledger witness and Compliance/Operations reviewers confirm a single authoritative terminal outcome.

A rollback means **returning the payment engine to a safe pre-settlement operating mode**, not deleting a transfer or rewriting an audit row. Append-only evidence must remain intact. If a transfer may have committed, the system must reconcile; it must not issue a compensating transfer merely because the original response timed out.

## DR failover scenarios

| ID | DR scenario | Expected observable signals | Failover action | Rollback trigger | Evidence required |
|---|---|---|---|---|---|
| DR-F01 | Primary payment-engine instance becomes unavailable | Health check fails; Prometheus target down; Alertmanager notification delivered. | Route only idempotent, known-safe reads to the standby; hold uncertain writes until ownership/lease is confirmed. | Standby cannot prove exclusive ownership or duplicate processing is possible. | Target state, alert ID, lease/leader record, routing decision, held requests. |
| DR-F02 | Primary PostgreSQL becomes unavailable | Connection failures, circuit breaker opens, migration/transaction errors, pool exhaustion. | Open circuit; stop writes; fail over to approved replica/recovery database only after schema and consistency checks. | Replica lag exceeds approved threshold, schema version differs, or write authority is ambiguous. | DB health, circuit transition, lag, schema checksum, role grants, recovery decision. |
| DR-F03 | PostgreSQL restore completes with inconsistent or incomplete data | Restore succeeds technically but row counts, checksums, or reconciliation differ. | Keep recovery environment isolated and read-only; do not reintroduce it to the payment path. | Any unexplained missing/extra record or failed ledger reconciliation. | Backup ID, restore logs, row/checksum comparisons, schema version, reconciliation report. |
| DR-F04 | TigerBeetle primary cluster loses quorum during DR switch | Ledger health fails while application is attempting failover. | Fence all settlement paths; do not promote an unverified ledger node. | Quorum cannot be established or the promoted view conflicts with the last trusted facts. | Cluster and quorum evidence, fencing event, promotion decision, held transactions. |
| DR-F05 | Provider rail unavailable during failover | Provider timeout/5xx, circuit open, webhook gap, or status unavailable. | Do not switch rails for an UNKNOWN payment unless the first rail’s status is conclusively non-submitted. | Any rail switch while original execution status is UNKNOWN, or provider and ledger statuses conflict. | Provider traces, circuit state, status lookup, coordinator decision, no-duplicate assertion. |
| DR-F06 | Monitoring/alert delivery unavailable | Prometheus scrape failure or Alertmanager delivery failure; no receiver acknowledgement. | Treat observability loss as an operational incident; suspend customer-impacting activity if coverage is required by policy. | Critical control can operate without required audit/alert visibility. | Target status, Alertmanager logs, receiver response, suspension decision, recovery test. |
| DR-F07 | WORM/evidence store unavailable or mutable | Upload failure, retention mismatch, object-lock validation failure, or digest mismatch. | Stop evidence-dependent release or failover approval; retain local encrypted transient logs only under approved procedure. | Any missing immutable evidence or inability to prove artifact integrity. | Object metadata, retention mode, digest comparison, access-denial test, incident record. |
| DR-F08 | Recovery exceeds approved RTO or loses data beyond approved RPO | Recovery timestamps exceed limits; restored event/ledger range is incomplete. | Keep service suspended, notify stakeholders, and open a CAP. | RTO/RPO breach, unresolved data loss, or inability to reconcile recovered state. | Start/end times, RTO/RPO calculation, missing-range analysis, CAP and approval. |

## DR rollback triggers

The DR exercise must automatically revert to the safe suspended state when any of the following occurs: the standby cannot prove exclusive write ownership; PostgreSQL schema or migration state differs from the approved release; TigerBeetle quorum or account binding is unverified; any payment is UNKNOWN and the failover path would submit a second command; reconciliation produces any unexplained discrepancy; health-gate or critical alert delivery fails; WORM retention or digest verification fails; recovery exceeds the approved RTO/RPO; or an unauthorized operator attempts to alter the recovery decision.

The safe rollback sequence is to suspend new payment execution, fence the promoted worker or node, preserve immutable logs, return routing to the last trusted healthy path only after health and ownership checks pass, reconcile all in-flight and UNKNOWN operations, and obtain an Operations/Treasury/Compliance decision before resuming. If the trusted path cannot be re-established, remain suspended and escalate.

## Required evidence fields

Every failure and rollback record must include the release SHA, environment, scenario ID, injected fault, start/end timestamps in UTC, operator and reviewer subjects, request and correlation IDs, idempotency key, payload digest where applicable, ledger/DB/provider states, alert IDs, decision and authority, recovery time, reconciliation result, WORM object path, artifact SHA-256, and CAP reference.

## Pass/fail rule

The scenario passes only when the platform detects the fault, prevents unsafe financial duplication, records an attributable decision, performs recovery or remains safely suspended, reconciles the resulting state, and retains immutable evidence. A test that merely returns an HTTP error is insufficient. A scenario fails if it silently retries, settles twice, loses evidence, permits unapproved failover, or reports success without authoritative reconciliation.
