# Quality Assurance Surveillance Plan (QASP) — UmojaFlowOS
Date: 2026-10-04 · Branch: audit-remittance-bdc-antiwipe-performance-2026-09-24 · PR #45

## 1. Purpose

This QASP defines how the quality of UmojaFlowOS — an evidence-first B2B
control plane for African cross-border payments — is surveilled: what is
measured, against which standard, by which method, at what frequency, and
what happens when a standard is not met. It converts the four audit waves of
2026-10-03/04 (feature→service→data mapping, frontend↔backend alignment,
database/middleware matrix, in-memory Map durability) from one-time events
into standing surveillance.

## 2. Scope

All deliverables on the platform: the TypeScript control plane (279 tRPC
procedures, 11 sub-routers), 9 backend services (Go/Rust/Python), 69
PostgreSQL migrations / 148 tables, 16 mandated middleware integrations,
frontend UI/PWA surfaces, and ML/advisory pipelines.

## 4. Roles and responsibilities

- **Contracting Officer's Representative (COR) equivalent:** platform owner — approves this QASP, accepts/rejects deliverables.
- **Surveillance executors:** CI pipeline (automated methods), module owners (per-domain), auditor role (adversarial probes).
- **Remediation owners:** the team owning the failing service/module; fixes land as dedicated waves under the same push+verify discipline used for Batch 4.

## 5. Surveillance cadence summary

- **Per PR:** items 1, 3, 5, 6, 8, 9, 10 (automated).
- **Per migration:** item 2.
- **Per release candidate:** item 7.
- **Quarterly:** items 3 and 4 full-repo sweeps (repeat the 2026-10-04 methodology).

## 6. Remediation and escalation

1. Any missed standard opens a tracked finding with a persistence/severity class (CRITICAL/MEDIUM/benign), mirroring the in-memory Map audit classification.
2. CRITICAL findings (business data at risk, duplicate-submission paths, RBAC bypass) block merge of the offending PR and trigger a fix wave with adversarial tests before closure.
3. Closure requires: fix implemented, adversarial test green, byte-exact push verification, and a dated audit doc under `docs/` — the same evidence chain as Batches 1–4.

## 7. Documentation and records

All surveillance outputs are records: audit docs in `docs/`, CI logs, k6/Lighthouse reports, and sha256 verification logs. Records are immutable once written (append-only audit trail), consistent with the platform's evidence-first design.

## 8. Known limitations (honest)

- Static wiring checks do not prove live connectivity; serviceBridge integrations remain disabled-by-default and activate via verified health checks.
- ML quality metrics derive from synthetic Nigerian generators until labeled historical data exists; this QASP surveils the *contract* (advisory-only, no fabrication), not production model accuracy.
